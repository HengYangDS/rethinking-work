# Work-chain design card

This is a teaching template, not a policy, authorization or second task ledger.
Use it to improve the task's existing brief or work record.

## Intended result

- Who will use the result, and for which decision or action?
- What is the exact deliverable and observable acceptance condition?
- Which data, repository, source version or application is in scope?

## Execution chain

| Step | Exact input and identity | Native capability | Output and next consumer | Failure or stop condition |
| --- | --- | --- | --- | --- |
| Acquire | | | | |
| Interpret | | | | |
| Execute | | | | |
| Verify | | | | |
| Retain and close | | | | |

Use only the steps the task needs. Existing source, state and progress owners
remain authoritative; link them instead of copying their changing state.

## Decision and effect boundaries

- Which ambiguity can the agent resolve from authorized evidence?
- Which choice changes business meaning, permission or irreversible effects?
- Which operations are deterministic, repeatable and idempotent?
- Which commit, submission or publication cannot be undone by cancellation?
- Who accepts the result, and who owns residual risk?

## Adoption comparison

Record the baseline and candidate on equivalent tasks. Include total elapsed
time, human preparation and review, rework, fees, maintenance and failures.
Do not infer causal improvement from unlike tasks or declare independence when
the evaluator has read the candidate's preferred answer.
